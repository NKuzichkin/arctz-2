# Фоновый сеанс на Android: уведомление с управлением и остановка при принудительном закрытии

Дата: 2026-08-17

## Задача

На Android приложение не переживает закрытие через меню недавних задач: процесс
убивается, а станок доигрывает то, что уже лежит в rx/planner-буфере FluidNC.
Пункт меню «Выход» (см. коммит `17c4bd1`) останавливает станок корректно, но
смахивание из недавних мимо него проходит.

Требуется:

1. Пока приложение связано со станком, держать в шторке уведомлений постоянное
   уведомление с состоянием и кнопками управления выполнением — по образцу
   музыкальных проигрывателей.
2. При принудительном закрытии приложения останавливать станок, без диалогов.

## Решения, принятые до дизайна

- Уведомление живёт **всё время, пока есть связь со станком**, а не только на
  время выполнения программы. Это единственный способ поймать смахивание из
  недавних во время джога или недоигранного длинного перемещения, и заодно
  Android перестаёт рвать Bluetooth при уходе приложения в фон.
- Кнопки: **Пауза/Продолжить** (одна кнопка, переключается по состоянию) и
  **Стоп**. Тап по телу уведомления открывает приложение.
- При принудительном закрытии выполняется **полная последовательность
  остановки** — та же, что при выходе: `StopAndDrainAsync` (`0x85` → сброс
  очереди приложения → `!` → ожидание подтверждённой остановки → `0x18`), затем
  разрыв связи.
- Кнопка «Стоп» в уведомлении повторяет поведение кнопки «Стоп» в приложении
  (feed hold + сброс очереди), а не полную последовательность выхода.

## Ограничения платформы

- **Android 13+** требует runtime-разрешение `POST_NOTIFICATIONS`. Без него
  сервис работает, но уведомления не видно.
- **Android 14+** требует объявленный `foregroundServiceType`. Используется
  `connectedDevice` с разрешением `FOREGROUND_SERVICE_CONNECTED_DEVICE`:
  приложение управляет подключённым по Bluetooth устройством.
- **Гарантии остановки нет.** `OnTaskRemoved` вызывается при смахивании из
  недавних, и foreground-сервис даёт процессу дожить до отправки команд. Но
  «Закрыть принудительно» в настройках, агрессивный менеджер питания (Xiaomi,
  Huawei, Samsung) или падение процесса убивают процесс мгновенно — послать в
  этот момент уже нечего. Обойти это из приложения нельзя.

## Архитектура

Логика, содержащая решения, живёт в ядре и покрывается тестами; в
`ArctZ.Android` остаются только вызовы Android API. Причина жёсткая:
`ArctZ.Tests` не может ссылаться на `net10.0-android`, поэтому всё, что попало
в голову, тестами не покрывается в принципе.

`ProgramViewModel` зарегистрирован в DI синглтоном
(`ServiceCollectionExtensions.AddArctZCore`), а Android-сервис работает в том же
процессе — значит, сервис получает ровно тот экземпляр, с которым работает UI.
На этом держится весь дизайн.

### A. Состояние фонового сеанса (ядро)

```csharp
namespace ArctZ.Services.App;

public readonly record struct BackgroundSessionState(
    string Title,      // имя программы либо "ArctZ"
    string Status,     // готовый StatusLabel: «Выполнение», «Пауза», «Переподключение…»
    bool CanPause,     // PlaybackState.Running
    bool CanResume,    // PlaybackState.Paused
    bool CanStop);     // Running | Paused
```

Проектор — чистая функция от `PlaybackState`, `ConnectionState`, имени
программы и уже существующего `StatusLabel`. Второй источник правды о состоянии
не заводится: `StatusLabel` собран в `ProgramViewModel` и покрыт тестами
(`ProgramViewModelStatusLabelTests`).

### B. Seam (ядро)

```csharp
public interface IBackgroundSessionHost
{
    void Update(BackgroundSessionState state);  // показать/обновить, идемпотентно
    void Stop();                                // убрать уведомление, остановить сервис
}
```

`NullBackgroundSessionHost` регистрируется в `AddArctZCore()` — Desktop, Browser
и iOS ничего не замечают. Android-голова подменяет регистрацию своей
реализацией.

### C. Координатор (ядро)

`BackgroundSessionCoordinator` — синглтон, подписанный на `PropertyChanged`
`ProgramViewModel` (`PlaybackState`, `ProgramName`, `StatusLabel`) и
`ConnectionViewModel` (`Session`, `ConnectionState`, `DeviceStatus`). Вызывает
`Update` при каждом изменении и `Stop()`, когда `Connection.Session` стало
`null`.

Признак «связь есть» — именно `Session`, а не `ConnectionState`: при обрыве
`ConnectionState` уходит в `Reconnecting`, но станок никуда не делся и сеанс
обязан пережить переподключение. Обнуляется `Session` только при явном
отключении (`ManualDisconnectAsync`) и при закрытии приложения.

Поднимается в `App.OnFrameworkInitializationCompleted` рядом с существующим
резолвом `ProgramViewModel`.

### D. Выход без диалога (ядро)

`ProgramViewModel.ShutdownAsync(bool confirmIfRunning = true)`. Путь
принудительного закрытия зовёт с `false`: подтверждение не показывается никогда,
остальное — стоп-последовательность и разрыв связи с подавлением
автоподключения — идентично существующему пути.

### E. Android: сервис

`MachineSessionService : Service`, `ForegroundServiceType = ConnectedDevice`,
`Exported = false`:

- `OnStartCommand` разбирает `Action` интента (`pause` / `resume` / `stop` /
  `refresh`) и выполняет соответствующую команду синглтона `ProgramViewModel`;
- уведомление собирается из последнего `BackgroundSessionState`; кнопки —
  `PendingIntent` на себя же;
- тап по телу уведомления открывает `MainActivity`;
- `OnTaskRemoved` асинхронно выполняет `ShutdownAsync(confirmIfRunning: false)`,
  затем `StopForeground` + `StopSelf`. Работа не должна блокировать главный
  поток: `OnTaskRemoved` вызывается именно на нём.

`AndroidBackgroundSessionHost : IBackgroundSessionHost` хранит последнее
состояние, при первом `Update` поднимает сервис через `StartForegroundService`,
дальше обновляет уведомление через `NotificationManager.Notify`, по `Stop()`
останавливает сервис.

### F. Манифест и разрешения

- Добавить `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE`,
  `POST_NOTIFICATIONS`.
- `MainActivity` получает `LaunchMode = SingleTask`: иначе тап по уведомлению
  поднимет вторую копию активности поверх живой.
- `POST_NOTIFICATIONS` запрашивается вместе с Bluetooth-разрешениями
  (`AndroidPermissions`), только на API 33+.

## Тестирование

Покрываются тестами (`ArctZ.Tests`):

- проектор: `Running` → Пауза + Стоп; `Paused` → Продолжить + Стоп;
  подключено без программы → без кнопок; программа без имени → заголовок
  «ArctZ»;
- координатор: изменения состояния ViewModel → вызовы фейкового хоста;
- `ShutdownAsync(confirmIfRunning: false)`: диалог не показывается,
  станок останавливается, связь рвётся.

Не покрывается: всё в `ArctZ.Android` — по причине, названной выше. Поэтому в
голове не должно остаться ни одного решения, только вызовы Android API.

Живая проверка выполняется по правилу из `CLAUDE.md`: сборку APK, установку на
устройство и запуск делает пользователь, после чего задаются поточечные вопросы
по каждому сценарию (уведомление появилось и исчезло, каждая кнопка, смахивание
из недавних во время программы и во время джога).
