# Перемещения через G93 (inverse time feed) — дизайн

Дата: 2026-08-18

## Проблема

Джиб — устройство кинематографических проездов, и постановщик мыслит
временем: «из точки 1 в точку 2 за 15 секунд». Сейчас программа хранит
скорость (`KeyPoint.FeedRateUnitsPerMin`, всегда `500`, редактора нет), а
компилятор выдаёт `G1 ... F<ед/мин>` в подразумеваемом режиме G94. Чтобы
получить нужную длительность, пользователю пришлось бы делить дистанцию по
четырём осям на подачу вручную — и промахиваться каждый раз, когда точку
двигают.

G93 (inverse time feed) задаёт ровно то, что нужно: `F = 1 / t`, где `t` —
время блока в минутах. Прошивка сама раскладывает это на скорости осей,
и все четыре оси приходят в точку одновременно.

## Решение в одном абзаце

`KeyPoint.FeedRateUnitsPerMin` заменяется на `TransitionSeconds`. Все
строки движения программы формируются как
`G93 G1 X.. Y.. Z.. A.. F<60/t_сек>`, причём `G93` пишется в каждой строке.
В редакторе точки появляется поле «Время перехода, с». Оценка длительности
шага перестаёт быть оценкой — она берётся прямо из заданного времени.

## Модель данных

`ArctZ/Services/Program/KeyPoint.cs`:

```csharp
public sealed record KeyPoint(
    Guid Id,
    int Number,
    string? Label,
    MachinePose Pose,
    double DwellSeconds,
    double TransitionSeconds,   // было: double FeedRateUnitsPerMin
    EaseMode Ease,
    bool ContinuousBlend)
```

Семантика позиционная — та же, что у `DwellSeconds`/`Ease`/`ContinuousBlend`
сегодня: сегмент `i` (переход `KeyPoints[i] → KeyPoints[i+1]`) берёт
настройки у точки-получателя, то есть `KeyPoints[i+1].TransitionSeconds`.
Значение точки №1 используется только в одном месте — переход «встать в
начальную позицию по завершении» (`RunReturnToStartMoveAsync`).

Значение по умолчанию — **5 секунд**, константа
`InverseTimeMove.DefaultTransitionSeconds` (живёт рядом с правилом
непозитивного времени, которое её и применяет). Используется при захвате точки
(`CaptureKeyPoint`, `ProgramViewModel.cs:516`) вместо нынешних
`FeedRateUnitsPerMin: 500`.

**Хранилище.** Миграции нет. `JsonFileProgramStorage` десериализует
`JibProgram` напрямую через `System.Text.Json`; старые файлы содержат
`FeedRateUnitsPerMin`, которого в записи больше нет — поле будет молча
проигнорировано, а `TransitionSeconds` получит `0` из десериализатора.
Это подхватывает общее правило «непозитивного времени» (см. ниже): такая
точка едет за 5 секунд по умолчанию, а не мгновенно. Пункт для проверки на
живом железе: открыть старую программу и убедиться, что она едет спокойно.

## Формат команды

Новый общий хелпер (`ArctZ/Services/Program/InverseTimeMove.cs`), чтобы
формат жил в одном месте — сейчас та же строка дублируется в трёх:

```csharp
public static string Line(MachinePose pose, double seconds) =>
    $"G93 G1 X{Axis(pose.X)} Y{Axis(pose.Y)} Z{Axis(pose.Z)} A{Axis(pose.A)} F{Feed(seconds)}";
```

Три решения, зафиксированные в этом формате:

**1. `G93` в каждой строке.** Режим модальный, и держать его глобально
значит восстанавливать `G94` во всех путях останова — обычное завершение,
`Stop`, `StopAndDrainAsync`, ошибка, выход из приложения, обрыв связи. Любой
пропуск оставляет машину в inverse-time режиме, где следующая же команда без
`F` даёт `error:2`. Повторение `G93` в каждой строке снимает вопрос
полностью: ни один путь не зависит от того, в каком режиме машина осталась.
Стоимость — четыре лишних байта на строку.

`G94` обратно приложение **не отправляет никогда**. Джог (`$J=`) на это не
влияет: jog-команды в GRBL/FluidNC разбираются в собственной копии
модального состояния и на режим подачи программы не смотрят.

**2. Точность `F`.** Существующий формат `0.###` для inverse-time
недостаточен: переход на 3600 с даёт `F = 60/3600 = 0.0166667`, что
`0.###` округлит до `0.017` — ошибка ~2% (≈70 секунд). `Feed()` использует
`0.#######` (`InvariantCulture`). Координаты остаются на `0.###`.

**3. Непозитивное время.** `t <= 0` дало бы `Infinity`/`NaN` в строке.
Клампить к «почти нулю» нельзя: это означало бы бросок на максимальной
скорости оси — худший из возможных ответов на пустое поле ввода или на
старый файл программы, где `TransitionSeconds` десериализуется в `0`.
Поэтому единое правило: `t <= 0` заменяется на
`InverseTimeMove.DefaultTransitionSeconds` (5 с). Правило живёт в одном месте —
в `InverseTimeMove`, — и обслуживает разом старые файлы, пустой ввод в
редакторе и любой будущий источник данных.

Проверок достижимости заданного времени приложение не делает — ни сверху
(`max_rate` оси), ни снизу (`v_min ≈ 2290 / steps_per_mm`, см.
`docs/firmware/fluidnc-slow-motion-limits.md`). Это осознанное решение:
FluidNC нарушает оба порога молча, но диагностика границ — отдельная задача.

## Компилятор траектории

`ArctZ/Services/Program/TrajectoryCompiler.cs`:

- `MoveCommand(pose, feed)` → `InverseTimeMove.Line(pose, seconds)`.
- `CompiledStep.EstimatedDurationSeconds` для простого сегмента — это ровно
  `segment.To.TransitionSeconds`, без вычислений.
- Хелперы `Distance()` и `EstimateDuration()` удаляются: евклидова
  дистанция по четырём осям больше нигде не нужна.
- `G4 P<сек>` для стоянок и обработка `StopsAtWaypoint` — без изменений.

### Ease-in/out переносится на времена

Профиль сохраняется: 6 подшагов, скорость 0.3x → 1.0x на первой трети,
1.0x в середине, 1.0x → 0.3x на последней трети (`FeedMultiplier`,
`MinFeedFraction = 0.3`). Меняется то, что распределяется: не подача, а время.

Подшаги равны по расстоянию (линейная интерполяция по равномерному `t`),
поэтому время i-го подшага обратно пропорционально множителю скорости:

```
w_i = 1 / FeedMultiplier(t_i)          // t_i = i / 6, i = 1..6
t_i_сек = TransitionSeconds * w_i / Σ w
```

Нормировка по `Σ w` даёт побочный выигрыш: суммарная длительность сегмента
с ease теперь **точно** равна заданной. С G94 она такой не была — там ease
растягивал сегмент на непредсказуемую величину.

`SegmentProgress` подшагов остаётся линейным по расстоянию (`i / 6`) — это
доля пути, а не времени, и её потребитель (подсветка/прогресс) не меняется.

## ViewModel

`ArctZ/ViewModels/ProgramViewModel.cs` — две ручные команды переходят на тот
же хелпер и то же время:

- `MoveMachineToKeyPointAsync` (`:650`) — «перейти к точке»; берёт
  `keyPoint.TransitionSeconds`. Стартовая поза произвольная, так что время
  соблюдается, а получившаяся скорость может отличаться от программной —
  это ожидаемо и не корректируется.
- `RunReturnToStartMoveAsync` (`:1228`) — возврат в начало; берёт
  `KeyPoints[0].TransitionSeconds`.

Локальные `FormatAxis`-склейки строк в обоих местах удаляются в пользу
`InverseTimeMove.Line`.

## UI: поле «Время перехода, с»

`ArctZ/ViewModels/KeyPointEditorViewModel.cs` — новое
`[ObservableProperty] double _transitionSeconds`, инициализируется из
источника, попадает в `Save()`:

```csharp
_onSave(_source with {
    Label = Label,
    Pose = new MachinePose(X, Y, Z, A),
    TransitionSeconds = TransitionSeconds,
    DwellSeconds = DwellSeconds });
```

`ArctZ/Views/MainView.axaml` — в сетке оверлея редактора точки
(`:330-341`) добавляется строка **над** «Стоянка, с»:

```
Время перехода, с   [TextBox]
Стоянка, с          [TextBox]
```

Поле показывается для всех точек, включая №1: у первой точки оно
управляет возвратом в начальную позицию по завершении программы.
Никаких предупреждений о достижимости и никаких правок значения в самом
редакторе: пустое или нулевое поле превращается в 5 секунд уже на этапе
формирования команды, общим правилом.

Суммарная длительность программы в шапке списка точек — **вне объёма**
задачи.

## Мок-устройство

`ArctZ/Services/Device/Simulation/MockDeviceTransport.cs` сейчас трактует
`F` как ед/мин и двигает каждую ось независимо с этой скоростью
(`AdvanceMotion`, `stepPerAxis = _feedUnitsPerMin / 60 * elapsed`). Со
строкой `G93 G1 ... F4` он поехал бы со скоростью 4 ед/мин, то есть на
порядки медленнее заданных 15 секунд, и симулятор перестал бы соответствовать
реальности.

Мок получает второй режим движения: если разобранная строка содержит `G93`,
он запоминает позу старта, целевую позу и длительность `60 / F` секунд, а
`AdvanceMotion` линейно интерполирует позу по накопленному времени — все оси
приходят одновременно, ровно как у координированного движения. Режим G94
(и джог `$J=`, который остаётся на подаче) продолжает работать по-старому.

В строке статуса `FS:` мок сообщает эффективную подачу — дистанцию блока,
делённую на длительность, в единицах в минуту, — а не значение `F` из
inverse-time строки.

## Что осознанно не делается

- **Проверка достижимости времени.** По решению пользователя: команда
  уходит как введена, предупреждений нет.
- **Миграция старых программ.** Вместо неё — общее правило непозитивного
  времени, см. выше.
- **Асимметрия обратного прохода (PingPong).** `ReversedProgram`
  (`ProgramViewModel.cs:1182`) разворачивает список точек, поэтому сегмент
  обратного прохода берёт настройки соседней точки, а не той же самой:
  переход A→B на прямом ходу и B→A на обратном получают разные времена.
  Это существующее поведение, оно так же работало для подачи, стоянки и
  ease. С явными временами асимметрия становится заметнее, но исправление
  меняет семантику всех четырёх настроек сразу и должно идти отдельной
  задачей.
- **Суммарное время программы в UI.**
- **G93 для джога.** Джог остаётся скоростным по своей природе — стик
  задаёт скорость, а не время.

## Проверка на устройстве

По правилу из `CLAUDE.md` UI-проверка выполняется единственным способом:
собрать `ArctZ.Desktop`, запустить, попросить пользователя проверить и
задать поточечные вопросы через `AskUserQuestion` — отдельно про поле
«Время перехода, с» в редакторе точки, отдельно про фактическую
длительность проезда между двумя точками, отдельно про переход с ease,
отдельно про «перейти к точке» и возврат в начало, отдельно про джог после
обычного завершения программы: после *нормального* завершения (не
`Stop`/`StopAndDrainAsync`) soft reset не отправляется, значит контроллер
остаётся в режиме G93. Решение полагается на то, что `$J=` разбирается в
собственной копии модального состояния GRBL/FluidNC и не зависит от режима
подачи программы — это почти наверняка так (grbl 1.1 форсирует units-per-min
для джог-блока и требует собственный `F`, FluidNC этот код унаследовал), но
единственное подтверждение в ветке — мок-устройство, написанное под то же
предположение, то есть проверка получается циклической. Прогнать программу
до обычного конца, затем подвигать обоими стиками и убедиться, что скорость
джога нормальная и ответа `error:` нет.
