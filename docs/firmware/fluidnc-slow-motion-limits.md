# Ограничения FluidNC на медленных подачах

> **Справочник по прошивке** (не `DRAFT`): раздел «Как FluidNC ведёт себя» —
> факты, подтверждённые исходниками FluidNC (ветка `main`, прочитано
> 2026-08-18) и разбором issue в апстриме. Раздел «Что это значит для ArctZ»
> — выводы под нашу задачу, они черновые и подлежат проверке на реальном
> железе.

Джиб — устройство медленных движений: кинематографический проезд на 30° за
минуту это 30 единиц/мин, а «почти незаметный» наезд — единицы единиц в
минуту. Именно в этом диапазоне GRBL-совместимая математика движения
FluidNC перестаёт исполнять заданную подачу и **молча** едет быстрее. Ниже —
три независимых порога, откуда они берутся и что с ними делать.

## Коротко

| # | Порог | Величина | Что происходит при нарушении |
|---|---|---|---|
| 1 | `MINIMUM_FEED_RATE` планировщика | **1.0 ед/мин**, жёстко в прошивке | подача поднимается до 1.0, без `error`, без предупреждения |
| 2 | Минимальная частота шага (таймер + AMASS) | **≈38 шагов/с** → `v_min ≈ 2290 / steps_per_mm` ед/мин | движение идёт быстрее заданного, программа завершается раньше срока |
| 3 | Квантование по шагам | перемещение < 1 шага | строка исполняется мгновенно (нулевое время), тайминг «по строкам» ломается |

Порог 2 — самый жёсткий: при типовых `steps_per_mm` он в десятки раз выше
1.0 ед/мин, и именно он определяет реальную нижнюю границу скорости.
Эффективный минимум оси: `max(1.0, 2290 / steps_per_mm)`.

## Порог 1: планировщик клампит подачу до 1 ед/мин

Источник: [FluidNC#1715](https://github.com/bdring/FluidNC/issues/1715)
(«FluidNC silently won't let me set feed rate less than 1mm/min», открыт
18.04.2026, FluidNC v4.0.1).

Симптом из issue:

```
G1 X220 F10    ->  <Run|MPos:200.524,0.000,0.000|FS:10,0>   — исполняется как задано
G1 X220 F0.1   ->  <Run|MPos:200.524,0.000,0.000|FS:1,0>    — молча исполняется как F1
```

Причина (разбор в треде, подтверждён исходниками):

- `FluidNC/src/Config.h`:
  ```cpp
  // Sets the minimum feed rate the planner will allow. Any value below it will be set to this minimum
  // value. This also ensures that a planned motion always completes and accounts for any floating-point
  // round-off errors. Although not recommended, a lower value than 1.0 mm/min will likely work in smaller
  // machines, perhaps to 0.1mm/min, but your success may vary based on multiple factors.
  const double MINIMUM_FEED_RATE = 1.0;  // (mm/min)
  ```
- Парсер `F` (`GCode.cpp`) значение **принимает** и кладёт в `gc_state.feed_rate`
  как есть; клампит уже планировщик в `plan_compute_profile_nominal_speed()`
  (`Planner.cpp`): всё, что ниже `MINIMUM_FEED_RATE`, выполняется как
  `MINIMUM_FEED_RATE`.
- Это **не** ограничение парсера и не ограничение степпера — степпер просто
  потребляет посчитанную планировщиком номинальную скорость.

Два практических следствия:

1. **Никакого сигнала об ошибке нет.** Ответ на строку — обычный `ok`.
   Отличить «выполнено как заказано» от «выполнено на пороге» по протоколу
   нельзя (см. п. 2). Автор issue как раз просит хотя бы предупреждение;
   апстрим ответил «feel free to implement» — то есть ждать этого не стоит.
2. **Поле `FS:` статус-отчёта округляется до целого** и для сверки подачи
   непригодно:
   ```cpp
   uint8_t digits = config->_reportInches ? 1 : 0;
   msg << " F" << std::fixed << std::setprecision(digits) << gc_state.feed_rate;
   ```
   `F10.5` отчитается как `11`. Плюс важнее: `FS:` показывает
   **заказанную** (`gc_state.feed_rate`), а не фактически исполняемую
   планировщиком скорость — то есть даже неокруглённое значение не
   доказывало бы, что машина едет с этой скоростью.

Изменить порог можно только пересборкой прошивки (`MINIMUM_FEED_RATE` —
константа компиляции). Комментарий в самом `Config.h` допускает 0.1 ед/мин
на небольших машинах, но не гарантирует результат.

## Порог 2: минимум один шаг на сегмент и 16-битный период таймера

Источники: [FluidNC#1372](https://github.com/bdring/FluidNC/issues/1372)
(«G93 timing inaccurate», закрыт) и
[FluidNC#772](https://github.com/bdring/FluidNC/issues/772)
(«Problem with Feedrate»).

### Механика

Генератор шагов (`Stepper.cpp`, унаследован от GRBL) режет блок планировщика
на сегменты длительностью `DT_SEGMENT`:

```cpp
// StepperPrivate.h
const float DT_SEGMENT = (1.0f / (float(ACCELERATION_TICKS_PER_SECOND) * 60.0f));  // min/segment
// Config.h
const int ACCELERATION_TICKS_PER_SECOND = 100;   // => DT_SEGMENT = 10 мс
```

В каждом сегменте должен быть **хотя бы один шаг** — код специально
удлиняет сегмент, пока шаг не наберётся:

```cpp
float minimum_mm = mm_remaining - prep.req_mm_increment;  // Guarantee at least one step.
...
if (mm_remaining > minimum_mm) {  // Check for very slow segments with zero steps.
    dt_max += DT_SEGMENT;         // растягиваем сегмент, пока не наберётся шаг
```

Само по себе растягивание сегмента скорость не завышает. Завышает следующее:
период прерывания степпера хранится **в 16 битах**, и слишком большое
значение просто обрезается:

```cpp
// isrPeriod is stored as 16 bits, so limit timerTicks to the
// largest value that will fit in a uint16_t.
prep_segment->isrPeriod = timerTicks > 0xffff ? 0xffff : timerTicks;
```

Обрезка = «шаг сделан раньше, чем требовала расчётная скорость». Именно об
этом писал bdring в #1372: «We use a timer to control the time between steps.
Choosing the timer speed and resolution affects the speed range. If you allow
it to go slower it reduces how fast it can go».

### Численная оценка порога

Для ESP32 (`FluidNC/esp32/esp32/Platform.h`): `STEPPING_FREQUENCY = 20 000 000`
(тик 50 нс). AMASS (`maxAmassLevel = 3`) на медленных движениях делит период
до 8 раз, поэтому предельный интервал между физическими шагами:

```
t_step_max = 2^3 × 65535 тиков / 20 МГц ≈ 26.2 мс
f_step_min = 1 / t_step_max            ≈ 38 шагов/с
v_min      = 60 × f_step_min / steps_per_mm ≈ 2290 / steps_per_mm  [ед/мин]
```

Сверка с полевыми замерами из #772 (там мерили «на глаз», порядок совпадает):

| Ось из #772 | `steps_per_mm` | Расчёт `2290 / spm` | Наблюдалось |
|---|---|---|---|
| X/Y | 35.555 | ≈ 64 ед/мин | «реальный минимум 50–60 мм/мин» |
| Z | 200 | ≈ 11 ед/мин | «около 10–12 мм/мин» |

Ответ MitchBradley там же формулирует правило без формул: «60 mm/min is
1 mm/sec. At 200 steps/mm, that is one step every 5 milliseconds. The GRBL
stepping engine inside FluidNC has a maximum segment time of a few
milliseconds, and must do at least one step in each segment. If you need to go
slower — use drivers with a high degree of microstepping, so steps/mm is
higher. Another alternative is mechanical gearing».

Таблица эффективного минимума `max(1.0, 2290 / steps_per_mm)`:

| `steps_per_mm` (шагов на единицу G-code) | Минимальная реальная скорость |
|---|---|
| 100 | ≈ 23 ед/мин |
| 200 | ≈ 11 ед/мин |
| 400 | ≈ 5.7 ед/мин |
| 800 | ≈ 2.9 ед/мин |
| 1600 | ≈ 1.4 ед/мин |
| 3200 | 1.0 ед/мин (упирается в порог 1) |

### Как это выглядит снаружи

В #1372 автор гонял две платы с идентичными по времени программами
(200 движений `G93`, каждое по 41.7 мс, суммарно 8.33 с) и мерил
осциллографом по `M62/M63`:

- 4-осевая конфигурация: 8.3 с — как задумано;
- 1-осевая (мелкие перемещения, `steps_per_mm = 113.333`): **7.1 с** — на
  1.3 с (≈15%) быстрее.

Никакой диагностики прошивка при этом не выдаёт: `ok` на каждую строку,
`FS:` показывает заказанное значение. Единственный признак — программа
закончилась раньше расчётного времени.

Отдельно любопытно (комментарий автора 06.11.2024): дробление того же
маршрута на более короткие движения (500/800/833/1000 вместо 200)
уменьшало расхождение между платами до ~20 мс, но **суммарная** длительность
при этом уплывала сильнее (8.6 с вместо 8.33 с). То есть «нарезать помельче»
не лечит, а перераспределяет ошибку.

## Порог 3: перемещение меньше одного шага исполняется мгновенно

Второе объяснение из #1372 (сформулировано автором, подтверждено
MitchBradley): часть строк в медленной программе задавала перемещение,
которое после квантования по шагам давало **ноль шагов** (одинаковые
координаты подряд). Такая строка не превращается в блок движения и не
занимает времени вовсе.

Следствия:

- Длительность программы, набранная «числом строк × время строки», на
  медленных проездах не соблюдается: часть строк схлопывается.
- **Паузу нельзя выражать движением в ту же точку** — только `G4 P<сек>`.
- `G93` (inverse time feed) для задания длительности перехода на медленных
  движениях ненадёжен: он задаёт время, но время соблюдается лишь если
  каждое движение реально даёт шаги и не упирается в пороги 1–2.

## Сколько может длиться одна команда

Обратная сторона тех же порогов: раз скорость снизу ограничена, ограничено и
время одной команды. Ни таймаута, ни watchdog на длительность блока в
прошивке нет — граница берётся из механики.

### Что означает `ok`

`ok` — это «строка разобрана и принята», а не «движение закончилось». Два
класса команд ведут себя по-разному:

- **Движения** (`G0`/`G1`/`G2`/`G3`, `$J=`) подтверждаются сразу, как только
  блок помещён в планировщик. Если планировщик полон, парсер крутится в
  `while (plan_check_full_buffer())` (`MotionControl.cpp:74`) и `ok`
  задерживается до освобождения одного блока — при `planner_blocks: 16`
  (дефолт, `MachineConfig.h:131`) это может быть время выполнения всей
  накопленной очереди.
- **Синхронные команды** — те, что вызывают `protocol_buffer_synchronize()`
  (`G4`, `$H`, установка смещений, синхронные выходы), — сначала дожидаются
  опустошения планировщика и только потом исполняются. Их `ok` действительно
  означает «выполнено».

### Максимальное время движения

```
t_max = ход / v_min = ход × steps_per_unit / 2290   [минут]
```

(пока `steps_per_unit ≤ 2290`; выше вступает кламп 1 ед/мин и
`t_max = ход / 1.0` минут).

Для оси Z (0..360°) при 355 шагов/градус: `v_min ≈ 6.4 град/мин`, значит
полный оборот одной командой — максимум **≈56 минут**. При разрешении
2290 шагов/градус и выше те же 360° растягиваются уже до **6 часов**.

### `G4` — до 24.9 суток

```cpp
mc_dwell(int32_t(gc_block.values.p * 1000.0f));   // GCode.cpp:1807
```

Аргумент — `int32_t` миллисекунд, то есть предел ≈2 147 483 647 мс ≈ **24.9
суток**; отрицательное `P` отклоняется. Две детали:

- отсчёт (`NutsBolts.cpp:24`) — цикл по 1 мс с `protocol_execute_realtime()`
  внутри, поэтому пауза выходит **не короче** заданной, с дрейфом в плюс;
- единственный досрочный выход из цикла — `sys.abort()`, то есть **soft reset
  (`0x18`)**. Feed hold `!` паузу не прерывает.

### `G93`: заданное время ограничено длиной перемещения

В inverse time режиме `F = 1 / t`, где `t` — время в минутах (час это
`F0.0166667`). Планировщик превращает это в обычную скорость, домножая на
длину блока (`Planner.cpp:359-361`):

```cpp
block->programmed_rate = pl_data->feed_rate;
if (block->motion.inverseTime) {
    block->programmed_rate *= block->millimeters;
}
```

Дальше действуют те же клампы, поэтому `t_max = расстояние / v_min` — ровно
как для `G94`. Для оси Z при 355 шагов/градус:

| Перемещение | Максимальное время одной команды `G93` |
|---|---|
| 10° | ≈1.6 мин |
| 30° | ≈4.7 мин |
| 360° | ≈56 мин |
| час на 30° | недостижимо: нужно ≥4580 шагов/градус (≈1.65 млн шагов/оборот) |

Час одной командой на оси 0..360° потребовал бы перемещения ≈387°, то есть
невозможен в принципе.

Что важно помнить про `G93`:

1. **Превышение предела не диагностируется.** `F0.0166667` на коротком
   движении примется, вернётся `ok`, и движение отработает за
   `расстояние / v_min` — заказанный час молча станет несколькими минутами.
   Ошибку дадут только `F0` (`GcodeUndefinedFeedRate`, `GCode.cpp:1342`) и
   отрицательное `F` (`NegativeValue`, `GCode.cpp:922`).
2. **`F` обязателен в каждой строке движения** (`GCode.cpp:992-994`) — в
   отличие от `G94`, значение не модальное.
3. **Даже в пределах порогов время не соблюдается** — это и есть содержание
   #1372 (−15% на программе, где каждое движение формально укладывалось в
   допустимое).

### Следствия для ArctZ

- `BufferAwareCommandQueue` ждёт `ok` без таймаута — и это правильно:
  легальная команда может подтверждаться через десятки минут.
- `DeviceStopTimeout = 2 с` (`ProgramViewModel.cs:230`) — бюджет на
  торможение, а не на длину команды. Если остановку нажали во время `G4`,
  ждать опустошения буфера бессмысленно (`!` паузу не прерывает), и
  `WaitForEmptyBufferAsync` вернёт `false`; машину останавливает безусловный
  `0x18` следом (`DeviceSession.cs:127`).
- Длинный проезд набирается последовательностью движений (как и делает
  `TrajectoryCompiler`), а неподвижное удержание — через `G4`.

## Как двигаться медленнее

По убыванию предпочтительности:

1. **Поднять `steps_per_mm`** — микрошаг драйвера и/или механическая
   редукция. Это единственный способ, не требующий пересборки прошивки, и
   именно им закрыли #1372: автор поднял микрошаг TMC2209 до 64 (проблема
   почти ушла), затем перевёл драйверы в UART-режим и поставил 256 микрошагов
   — «the timing problem disappear[ed] completely».
   Плата за это: во столько же раз растёт требуемая частота шагов на
   максимальной скорости (потолок FluidNC — порядка 100–125 кГц, см.
   [`fluidnc-setup.md`](fluidnc-setup.md)), и UART-режим драйверов
   усложняет проводку.
2. **Пересобрать прошивку** с другими `MINIMUM_FEED_RATE` /
   `ACCELERATION_TICKS_PER_SECOND` (обе — константы в `FluidNC/src/Config.h`,
   через `config.yaml` не настраиваются). Апстрим предупреждает: расширение
   диапазона вниз урезает максимальную скорость, а код генерации сегментов
   (`Stepper.cpp`) — «gnarly» по формулировке MitchBradley. Для нас это
   означает отказ от стоковой прошивки, чего лучше избежать.
3. **Не пытаться ехать медленнее порога**: строить движение так, чтобы
   заданная подача всегда была выше `max(1.0, 2290 / steps_per_mm)`, а
   «медленность» кадра обеспечивалась редукцией, а не подачей.

## Что это значит для ArctZ

### 1. Оси джиба вращательные — считать порог в градусах

`steps_per_mm` в FluidNC — «шагов на единицу G-code», для наших осей это
шагов на градус (см. [`fluidnc-setup.md`](fluidnc-setup.md), секция `axes`).
Пример для панорамы (ось Z): мотор 200 шагов/об, микрошаг 1/32, редуктор 20:1
даёт `200 × 32 × 20 / 360 ≈ 355 шагов/градус` → минимальная реальная скорость
≈ `2290 / 355 ≈ 6.4 град/мин` ≈ 0.11 град/с (полный оборот примерно за
56 минут). Всё, что медленнее, машина отработает быстрее заказанного.

Отсюда критерий выбора привода: `steps_per_unit ≥ 2290 / v_min_желаемая`.
Для «1 градус в минуту» нужно ≈2290 шагов на градус, то есть ~824 000 шагов
на оборот выходного вала — это уже область высоких микрошагов плюс серьёзной
редукции. Это вход в
[`../hardware/mechanics.md`](../hardware/mechanics.md) (выбор редукторов) и в
итоговый `config.yaml`.

### 2. `TrajectoryCompiler` — ease-in/out подходит к порогу втрое ближе

`ArctZ/Services/Program/TrajectoryCompiler.cs` при `EaseMode.EaseInOut`
умножает подачу ключевой точки на `FeedMultiplier(t)`, минимум которого —
`MinFeedFraction = 0.3`. То есть на разгоне и торможении фактическая
заказанная подача равна `0.3 × F`, и порог достигается уже при
`F ≈ 3.3 × v_min`. При типовых значениях (5 секунд на переход по умолчанию
из `InverseTimeMove.DefaultTransitionSeconds`) запас есть, но при медленных
проездах края сегмента обрежутся первыми — визуально это «дёрганый вход в
движение» вместо плавного.

Оценка длительности при этом больше не вычисляется: `EstimatedDurationSeconds`
шага равен времени, которое приложение само и заказало в `G93`. Ошибка теперь
целиком на стороне прошивки — если та поехала быстрее заказанного, реальная
длительность окажется **короче** оценки, прогресс будет отставать, а конец
программы придёт раньше полосы (см. `project_progress_bar_time_interpolation_complete`).

### 3. `JogCommandFactory` — нижний клип 1.0 совпал с порогом случайно

`ArctZ/Services/Device/JogCommandFactory.cs:39`:

```csharp
var feed = Math.Max(1.0, force * _maxFeedUnitsPerMin);
```

Комментарий в протокольном документе объясняет `1.0` как «чтобы не слать
нулевую подачу»; численно это ровно `MINIMUM_FEED_RATE`, но реальный порог
оси (порог 2) в разы выше. Важнее второе: длина шага джога выводится из
подачи (`feed / 60 × interval × lookaheadFactor`). Если прошивка едет быстрее
заказанного, блок проходится быстрее, чем рассчитывал `JogScheduler`, и
планировщик станка опустошается раньше — это тот самый механизм рывков,
против которого и вводился `lookaheadFactor` (см.
`project_jog_flow_control_fix`). То есть на слабом отклонении стика
(`force` мал → подача мала) микро-подводка может стать заметно менее плавной
и менее точной, чем на среднем отклонении.

### 4. Проверять подачу по `FS:` бессмысленно

`FluidNcStatusParser` поле `FS:` сейчас не разбирает — и добавлять его как
источник истины о скорости не нужно: значение округлено до целого и отражает
заказанную, а не исполняемую подачу. Признак попадания в порог — расхождение
фактической длительности перехода с расчётной, а не содержимое `FS:`.

### 5. Паузы — только `G4` (уже так и сделано)

`TrajectoryCompiler` выдаёт паузу в точке как `G4 P<сек>`, а не как повторное
`G1` в ту же позицию. По порогу 3 это единственно верный вариант: движение с
нулевым числом шагов исполнилось бы мгновенно. Это не косметика, а
требование — фиксируем, чтобы при рефакторинге компилятора не «оптимизировали»
паузу в движение.

### 6. `G93` — принятый компромисс для длительностей переходов

Программа по ключевым точкам задаётся временем («проезд за 15 секунд»),
поэтому `TrajectoryCompiler` выдаёт переходы как `G93 G1 ... F<60/t_сек>`
(см. `docs/superpowers/specs/2026-08-18-g93-inverse-time-moves-design.md`).
Ограничение из #1372 при этом остаётся в силе: на медленных движениях `G93`
даёт систематическую ошибку времени (в замере автора ~15%), и приложение её
никак не диагностирует — по решению пользователя проверок достижимости
времени нет.

Что это значит на практике: заданное время — это то, что приложение просит
и на чём строит временную интерполяцию прогресса, а не гарантия. Чем ближе
подача к `v_min` оси, тем сильнее реальный проезд заканчивается раньше
полосы прогресса. Признак — та же разница фактической и расчётной
длительности, что и в разделе 4.

## Открытые вопросы и задачи

- [ ] Читать `$$` при подключении и извлекать `steps_per_mm` по осям
      (`$100..$103`), чтобы приложение знало реальный `v_min` каждой оси.
      Сейчас `$$` шлётся только из `JogDiagnosticsTransport` в диагностику и
      нигде не парсится.
- [ ] Ввести в модель ограничений (`MachineLimits`/`AxisLimits`) минимальную
      подачу `max(1.0, 2290 / steps_per_unit)` и клампить/предупреждать в
      `TrajectoryCompiler` — сейчас ни компилятор, ни редактор ключевых точек
      о нижнем пороге не знают.
- [ ] Решить, что делать с ease-in/out при подаче, близкой к порогу: снижать
      `MinFeedFraction` нельзя (усугубляет), варианты — поднимать нижнюю
      границу подачи сегмента или отключать ease для медленных переходов.
- [ ] Проверить пороги на реальном железе: снять фактическую длительность
      перехода при подачах вокруг расчётного `v_min` и сверить с заказанным
      через `G93` временем (`EstimatedDurationSeconds`). Формула выведена из
      исходников и сверена с замерами из чужих issue, но не с нашей машиной.
- [ ] Учесть критерий `steps_per_unit ≥ 2290 / v_min` при выборе редукторов и
      микрошага в [`../hardware/mechanics.md`](../hardware/mechanics.md).
