## Общая схема

```
[ArctZ приложение] --Bluetooth SPP (виртуальный COM-порт)--> [Плата FluidNC] --> [Двигатели осей]
        ^                                                            |
        |------------------- статус-ответы (G-code) <-----------------|
```

Приложение (`ArctZ/`) выступает управляющим клиентом: считывает ввод
(в текущей версии — `VirtualJoystick`, см.
[`../software/app-architecture.md`](../software/app-architecture.md)),
транслирует его в G-code команды и отправляет на плату по Bluetooth-serial
соединению, которое ОС предоставляет как обычный COM-порт.

## Транспорт (Bluetooth)

- Тип соединения: **Bluetooth Classic SPP** (Serial Port Profile, не BLE).
  При подключении к Bluetooth-прошивке FluidNC ОС создаёт обычный
  Bluetooth COM-порт — дальше с ним можно работать как с любым serial-портом
  (в т.ч. штатными G-code-отправителями и FluidTerm).
- FluidNC должна быть прошита именно **Bluetooth-сборкой** — ESP32 не может
  одновременно работать по WiFi и Bluetooth (один радиомодуль), см.
  [`../firmware/fluidnc-setup.md`](../firmware/fluidnc-setup.md).
- Имя устройства при поиске задаётся настройкой `$Bluetooth/Name` на плате
  (не в `config.yaml`, а через `$`-команду после прошивки).
- Не определено: сопряжение (pairing) при первом подключении — вручную
  через настройки ОС или средствами приложения.

## Диалект G-code (GRBL-совместимый, реализация FluidNC)

### Поддерживаемые G-коды

| Код | Назначение |
|---|---|
| `G0` | быстрый ход на максимальной скорости |
| `G1` | линейное перемещение с текущей подачей |
| `G2` / `G3` | дуга по часовой / против часовой стрелки |
| `G4 Pn.n` | пауза (dwell) на n.n секунд |
| `G10` | задать смещение системы координат |
| `G17`/`G18`/`G19` | выбор плоскости XY (по умолч.) / ZX / YZ |
| `G20`/`G21` | единицы: дюймы / миллиметры |
| `G28`/`G30` | быстрый ход в заранее заданную позицию |
| `G28.1` | задать предустановленную позицию 0 |
| `G38.2`–`G38.5` | стандартное зондирование (probing) |
| `G38.6`–`G38.9` | зондирование, специфичное для FluidNC |
| `G40` | отмена компенсации инструмента |
| `G43.1` | динамическое смещение длины инструмента (`G43 H<n>` — **не поддерживается**) |
| `G49` | сброс смещения длины инструмента |
| `G53` | ход в машинных координатах (без учёта рабочего смещения) |
| `G54`–`G59` | выбор системы координат (6 шт.; `G59.1`–`G59.3` **не поддерживаются**) |
| `G90`/`G91` | абсолютный / относительный режим позиционирования |
| `G92` | задать смещение текущей позиции |
| `G93`/`G94` | подача в режиме "обратное время" / единиц в минуту |

### Поддерживаемые M-коды

| Код | Назначение |
|---|---|
| `M0` | пауза программы |
| `M2`/`M30` | конец программы / конец с перемоткой |
| `M3`/`M4`/`M5` | шпиндель по часовой / против / стоп (в нашем случае, вероятно, не используется — нет шпинделя) |
| `M6` | смена инструмента |
| `M61` | задать текущий инструмент без физической смены |
| `M7`/`M7.1` | туманное охлаждение вкл/выкл |
| `M8`/`M8.1` | заливное охлаждение вкл/выкл |
| `M9` | охлаждение выкл (оба) |
| `M62`–`M65` | цифровой выход, синхронно/немедленно |
| `M66` | чтение цифрового входа (поддерживается только immediate mode 0) |
| `M67` | аналоговый выход (ШИМ, параметры `E`/`Q`) |

Команды шпинделя/охлаждения (M3–M9) для джиба, скорее всего, не нужны —
релевантны только оси движения (G0/G1) и jog-режим ниже.

## Jog-режим ($J=) — основной кандидат для live-управления джойстиком

GRBL/FluidNC jog-режим позволяет двигать оси в реальном времени без
модификации рабочей программы/состояния модалов. Синтаксис (по спецификации
Grbl, на которую ссылается вики FluidNC):

```
$J=G91 G21 X10 Y-5 F500
```

— `G91` (относительно), `G21` (мм), смещения по осям, `F` — обязательная
подача. Каждая новая `$J=` команда во время движения плавно подхватывает
новое направление/скорость (это и есть механизм live-джойстика — слать
новую `$J=` по мере изменения угла/силы). Отмена текущего jog — realtime
байт `0x85` (Jog Cancel), не обычная строковая команда.

## Realtime-команды (однобайтовые, выполняются немедленно, вне очереди)

| Байт | Действие |
|---|---|
| `?` | запрос статуса |
| `!` | feed hold (пауза движения) |
| `~` | cycle start / resume |
| `Ctrl+X` (`0x18`) | программный сброс |
| `0x84` | триггер safety door |
| `0x85` | отмена jog |

Это важно для нашего кейса: `!`/`0x85` — вероятные кандидаты на команду
"джойстик отпущен, остановиться немедленно", в отличие от обычных
G-code строк, которые встают в очередь.

## Прочие $-команды

| Команда | Назначение |
|---|---|
| `$H` / `$Home` | полный цикл хоминга; `$H<ось>` — хоминг одной оси |
| `$X` / `$Alarm/Disable` | сброс состояния аварии |
| `$MD` / `$Motor/Disable`, `$ME` / `$Motor/Enable` | отключить/включить удержание моторов |
| `$I` / `$Build/Info` | версия прошивки и инфо об устройстве |
| `$G` / `$GCode/Modes` | текущее модальное состояние |
| `$?` | запрос статуса (строковая форма) |
| `$S` / `$Settings/List`, `$$` | список текущих настроек |
| `$Bye` | перезагрузка платы |

## Формат статус-ответа

Управляется настройкой `$Report/Status` (аналог Grbl `$10`): 0 — рабочие
координаты без буфера, 1 — машинные координаты без буфера, 2/3 — то же с
информацией о буфере. Пример:

```
<Idle|WPos:0.000,-80.000,-10.540|Bf:15,128|FS:0,0|Ov:100,100,100>
```

Поля: состояние (`Idle`/`Run`/`Jog`/…), рабочая позиция по осям, буфер,
текущая подача/скорость шпинделя, оверрайды.

## От джойстика к G-code

Сейчас `VirtualJoystick` отдаёт `Force` (0..1), `AngleDeg`/`AngleRad`,
дискретное `Direction` (8 румбов) и сырые `X`/`Y`. 

**Маппинг осей джойстика на оси устройства:** левый джойстик X/Y → машинные оси X/Y (подъём/опускание и поворот стрелы), правый джойстик X/Y → машинные оси Z/A (панорамирование и наклон камеры). Реализовано в `ArctZ/ViewModels/JoystickInputMapper.cs` и `ArctZ/Services/Device/JogCommandFactory.cs`.

Реализовано (`JogCommandFactory`/`JogScheduler`, тесты —
`ArctZ.Tests/Services/Device/JogCommandFactoryTests.cs`,
`JogSchedulerTests.cs`):

- `Force` (0..1, максимум по обоим стикам) конвертируется в `F` линейно,
  относительно настраиваемого `maxFeedUnitsPerMin` (минимум 1, чтобы не
  слать нулевую подачу).
- `$J=` отправляется по таймеру (`IPeriodicTimer`/`JogScheduler`), а не на
  каждое `JoystickMove` — интервал задаётся при создании `JogScheduler`,
  не хардкодится.
- Длина шага **выводится** из подачи и интервала таймера
  (`feed/60 × interval × lookaheadFactor`), а не задаётся константой. Блок,
  чьё время прохода не связано со скоростью отправки, либо истощает
  планировщик (тот тормозит до нуля на последнем блоке очереди — оператор
  чувствует это как рывки), либо забивает его на секунды вперёд.
  `lookaheadFactor` держится чуть выше 1, чтобы джиттер таймера/канала не
  опустошал очередь.
- Поток ограничен с двух сторон: не более `MaxOutstandingJogs`
  неподтверждённых `$J=` (мелкая зернистость между статус-репортами) и не
  более `MaxQueuedPlannerBlocks` блоков в планировщике станка, считая по
  полю `Bf:` статус-репорта. Без этого запись в порт блокируется на
  переполненном буфере, а на Desktop блокирующий `SerialPort.WriteLine`
  выполняется внутри залоченного `SerialEventQueue` — тогда `0x85` не
  успевает уйти и станок не останавливается по отпусканию стика.
- `ok`/`error` на `$J=` не принадлежат очереди `BufferAwareCommandQueue`
  (jog идёт мимо неё): `DeviceSession` сначала предлагает строку
  `IJogScheduler.TryHandleAck()` и только при отказе отдаёт её очереди
  команд — иначе `error` от переполнения буфера отменяет ожидающие строки
  выполняемой программы.
- При остановке джога (`JogScheduler.Stop()`, вызывается из
  `DeviceSession.EndJog()`) шлётся realtime `0x85` (jog cancel) через
  `IRealtimeCommandChannel`, а не обычная G-code строка.

## Обработка ошибок и статусов

Реализовано в `DeviceSession`/`FluidNcStatusParser`/`FixedDelayReconnectPolicy`
(тесты — `DeviceSessionReconnectTests.cs`, `FluidNcStatusParserTests.cs`):

- Разрыв соединения во время движения — `IDeviceTransport.Disconnected`
  переводит `DeviceSession` в `ConnectionState.Reconnecting` и запускает
  цикл переподключения по `IReconnectPolicy` (`FixedDelayReconnectPolicy`);
  джог и опрос статуса останавливаются на время разрыва.
- Парсинг статус-ответов (`<Idle|WPos:...|Bf:...>`) — `FluidNcStatusParser`,
  результат отражается в `DeviceSession.DeviceStatus`/`DeviceStatusChanged`.
  На данный момент разбираются состояние, `WPos` и `Bf:`; `MPos`/`FS`/`Ov`/
  `Ln`/`Pn`/`SD` не парсятся — добавить при необходимости отображать их в UI.
- `error:N` обрабатывается `BufferAwareCommandQueue.HandleError` (отклоняет
  команду, сигнал `CommandRejected`); `ALARM:N` — событие
  `DeviceSession.AlarmTriggered`. Список кодов алармов (`$A`/`$Alarms/List`)
  в UI пока не расшифровывается — приходит только числовой код.
- Переподключение после потери связи — реализовано (см. выше); политика
  количества попыток и задержки — `IReconnectPolicy`/`FixedDelayReconnectPolicy`.

- [ ] Библиотека для serial/Bluetooth-COM на стороне .NET, кроссплатформенно
